# go-push-service

秒杀结果的实时推送服务。用 Go + WebSocket 把"抢到了"从后端主动推给浏览器，替掉前端轮询。

> 这是我从一个 Java 秒杀系统（黑马点评）里拆出来的组件：Java 那边下单成功后往 Redis 发一条结果，这个服务订阅到之后，通过长连接推给对应的用户。

## 为什么要单独拆一个服务

原来的做法是前端每隔 1 秒问一次"我抢到了吗"。三个问题：

1. 每次轮询都要新建 HTTP 连接、带一堆 header，几万人在线时接口被自己打爆
2. 结果有延迟，最坏要等 1 秒
3. 大部分请求都是"还没好"，纯浪费

换成推送之后，连接建一次一直用着，后端有结果才推。**一万个用户同时挂着，就是一个进程里一万个 goroutine，占用几十 MB。**

## 链路

```
浏览器 ──HTTP 下单──▶ Java 秒杀服务 ──写结果──▶ Redis (seckill:result)
                                                      │
浏览器 ◀──WebSocket 推送──────────────────────  Go 推送服务（本项目）
                                                      │
                                                    订阅
```

Java 侧只改了几行：原来 `return "排队中"`，现在多一步 `redisTemplate.convertAndSend("seckill:result", uid + ":" + result)`。

## 快速开始

需要 Go 1.22+ 和一个跑着的 Redis。

```powershell
# 1. 拉依赖
go mod download

# 2. 起服务（默认监听 :8080，连 127.0.0.1:6379）
go run .

# 3. 另开一个窗口，连一条 WebSocket
#    浏览器控制台里执行：
#    const ws = new WebSocket('ws://localhost:8080/ws?uid=1001');
#    ws.onmessage = e => console.log(e.data);

# 4. 发一条结果
redis-cli publish seckill:result "1001:抢到了"
```

浏览器控制台会打出 `抢到了`。

## 几个只有靠测才能发现的问题

都在 [`FIXES.md`](FIXES.md) 里写清了原因和改法，这里挑三个最有代表性的：

**同一用户重连会把自己的新连接删掉。** 用户断网重连时，旧连接还没断干净、新连接已经注册进表；旧连接收尾时执行 `delete(conns, uid)`，删掉的是新连接。这个用户之后**永久收不到消息**。修法是删之前比对指针：只有表里存的还是自己才删。跑通测不出、压测也测不出，只有专门构造重连场景才能发现。

**加了心跳才会踩到并发写。** gorilla/websocket 规定同一个连接同一时刻只能有一个 goroutine 在写，否则 panic。心跳 goroutine 和推送逻辑会同时写，所以每个连接要配一把锁——Hub 那把锁保护的是"谁上线谁下线"，每连接的锁保护的是"这条连接别被两个 goroutine 同时写"。

**浏览器只回 pong，从不主动发 ping。** 所以服务端不发心跳的话，60 秒后连接会被自己的读超时踢掉。

## 已知限制

- **消息可能丢**：用的是 Redis `Pub/Sub`，不持久化，服务重启那一下的消息收不到。生产环境应该换 `Stream` + 消费组，重启后从上次 offset 续上。
- **单机**：连接表在进程内存里。多实例部署时，每台只持有本机在线用户的连接，需要靠 Redis 广播到所有实例，谁有谁推。
- **每条推送都同步打日志**：定位问题方便，但压测显示日志本身会拖慢吞吐（1000 连接的 P50 比 2000 连接还高就是这个原因）。下一步改成开关控制。
- 没有鉴权：连上就推，生产环境需要用 token 换 uid。

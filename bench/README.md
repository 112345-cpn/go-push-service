# 压测怎么自己跑

> **先看这段**：下面所有命令都是 **PowerShell** 写法（你 GoLand 的终端默认就是它）。
>
> 别用 Git Bash 那套 `/e/xxx` 路径和 `&&`，PowerShell 不认：
> - `cd /e/goplay/gopush` → 会变成 `E:\e\goplay\gopush` 报「路径不存在」
> - `cmd1 && cmd2` → 报「不是此版本中的有效语句分隔符」
>
> PowerShell 里路径用反斜杠，串命令用分号 `;`。

这个目录里有三个工具：

| 工具 | 干什么 |
|---|---|
| `probe` | 只连一条连接，看消息能不能收到。确认"服务是不是活的" |
| `loadtest` | 建 N 条连接 + 发 M 条消息，量吞吐、延迟、内存 |
| `reconnect` | 模拟"同一用户断网重连"，验证旧连接收尾不会把新连接误删 |

---

## 一、跑之前先做三件事

```powershell
# 1. 确认 Redis 活着（回 PONG 就对了）
E:\Redis-8.6.1-Windows-x64-msys2-with-Service\redis-cli.exe ping

# 2. 进项目目录（go.mod 在这个目录里，进错了 go build 会报 found not found）
cd E:\goplay\gopush

# 3. 编译（改过代码就重编）
go build -o gopush.exe .
go build -o bench\loadtest.exe .\bench\loadtest
go build -o bench\probe.exe .\bench\probe
go build -o bench\reconnect.exe .\bench\reconnect
```

**一行一条，不要写成 `a && b`**。编完 `ls` 一下，能看到 `gopush.exe` 和 `bench\` 下面三个 exe 就对了。

---

## 二、先跑一次单条连接，确认没坏

需要两个 PowerShell 窗口。

**窗口 A** —— 起服务（前台跑，能看日志）：

```powershell
cd E:\goplay\gopush
.\gopush.exe
```

**窗口 B** —— 起探针：

```powershell
cd E:\goplay\gopush
.\bench\probe.exe
```

窗口 B 会卡在那儿等消息。这时候开**第三个窗口**发一条：

```powershell
E:\Redis-8.6.1-Windows-x64-msys2-with-Service\redis-cli.exe publish seckill:result "1001:抢到了"
```

正常情况应该是：

- `publish` 返回值 **1**（1 个订阅者）
- 窗口 A 打印 `已推送给1001:抢到了`
- 窗口 B 打印 `收到: 抢到了`

**如果 `publish` 返回 0，说明 Go 那边没订阅上**，先别压测，去查 Redis 有没有连上。

## 三、测一下重连（30 秒，但能测出别人测不出的问题）

服务还在窗口 A 跑着，窗口 B 执行：

```powershell
cd E:\goplay\gopush
.\bench\reconnect.exe
```

期望输出最后一行是：

```
结果: 成功 —— 新连接收到「重连后应该收到这条」
```

如果是「失败 —— 新连接没收到消息」，说明那个重连 bug 又回来了。

## 四、正式压测

服务在窗口 A 跑着，窗口 B 执行：

```powershell
cd E:\goplay\gopush
.\bench\loadtest.exe -conns 1000 -msgs 2000
```

参数就五个，都有人话解释：

| 参数 | 默认 | 什么意思 | 什么时候改 |
|---|---|---|---|
| `-conns` | 500 | **同时挂多少条连接**（模拟多少用户在线） | 想看承载上限就往上加，1000 → 2000 → 5000 |
| `-msgs` | 1000 | **一共推多少条消息** | 想看吞吐就加大，2000 ~ 5000 |
| `-batch` | 50 | 建连接时的并发度 | 机器差就调小，建连失败多就调小 |
| `-pub` | 20 | 往 Redis 发消息的并发度 | 发布跟不上就调大 |
| `-wait` | 30s | 等消息收齐的最长时间 | 消息多、延迟高时调大 |

**跑默认值就能出结果**，别的不用管。

## 五、结果怎么读

真实跑出来的一份输出（2000 连接 / 3000 消息）：

```
=== 阶段一：建立 2000 条连接（并发度 50）===
建连前服务内存：15.4 MB
成功 2000 / 失败 0，总耗时 215ms，建连速率 9297 条/秒
建连耗时 P50=5.0577ms P95=8.0994ms P99=10.4255ms 最大=11.582ms
连接全部在线后内存：79.7 MB
每条连接平均占用：33 KB
=== 阶段二：发布 3000 条消息（并发 20）===
发布完成，耗时 142ms，发布吞吐 21172 条/秒

========== 压测结果 ==========
连接数            : 2000 条（失败 0）
建连吞吐          : 9297 条/秒，总耗时 215ms
建连延迟          : P50=5.0577ms P95=8.0994ms P99=10.4255ms
服务内存          : 空载 15.4 MB -> 2000 连接 79.7 MB
单连接内存        : 约 33 KB
消息收发          : 发出 3000 条，收到 3000 条，丢失 0 条
端到端延迟        : P50=16.2606ms P95=30.4512ms P99=31.5047ms 最大=32.4675ms
从发布到全部收齐  : 192ms，端到端吞吐 15592 条/秒
==============================
```

逐行翻译：

- **建连速率**：一秒能接多少人进来。越高越好。
- **P50 延迟**：一半人的延迟比这个低。**看这个，别看平均值。**
- **P95 / P99**：最慢那 5% / 1% 的人有多慢。**这才是体验的真相**——平均值好看但 P99 很差，说明有少数人卡死。
- **单连接内存**：每多一个人在线，服务多吃多少内存。乘上目标用户数就知道要几台机器。**面试官最想听这个数。**
- **丢失条数**：必须是 0。不是 0 就是有 bug。
- **端到端延迟**：从 Redis 收到消息，到客户端手上，中间多少毫秒。

## 六、我这台机器上实测的三组（都保留在 logs/ 里）

| 连接数 | 消息数 | 建连速率 | 内存 | 单连接 | 丢失 | P50 | P95 | P99 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 200 | 300 | 7458 条/秒 | 25.4 MB | 51 KB | 0 | 2.1 ms | 6.4 ms | 8.1 ms |
| 1000 | 2000 | 8072 条/秒 | 53.3 MB | 39 KB | 0 | 25.0 ms | 39.4 ms | 40.4 ms |
| 2000 | 3000 | 9297 条/秒 | 79.7 MB | 33 KB | 0 | 16.3 ms | 30.5 ms | 31.5 ms |

**你自己重跑，量级应该一样，具体数字会有点浮动**（机器负载不同）。填进 `RESULTS.md` 就行。

看这组数能发现两件事：

1. **单连接内存从 51KB 降到 33KB**：连接少的时候，固定开销（Redis 客户端、缓冲池）摊到每条上显得多；连接一多，固定开销被摊薄，趋于真实的 33KB。
2. **1000 连接的 P50（25ms）比 2000 的（16ms）还高**：这不正常。原因是**服务端每推一条消息都 `fmt.Printf` 一次**，2000 条就是 2000 次同步写文件，日志成了瓶颈。**这就是你的下一个改造点。**

## 七、给自己找三个改造点（简历上真正值钱的部分）

压测数据好看不是目的，**发现瓶颈并改掉它**才是。按难度从低到高：

### 改造一：把日志干掉，看吞吐变多少（最容易，20 分钟）

`listenRedis` 里每推一条都 `fmt.Printf`。生产环境这就是"每推一条消息同步写一次磁盘"。

做法：加一个 `-verbose` 开关，默认不打印。

```go
var verbose = flag.Bool("verbose", false, "是否打印每条推送")

// 用的时候：
if *verbose {
    fmt.Printf("已推送给%s:%s\n", uid, result)
}
```

改完再压一次同样参数，把两次数据放一起。**这个对比就是面试里的"我做了一次优化，吞吐从 X 提升到 Y"。**

### 改造二：把 Hub 的锁分片（中等，1 小时）

现在所有连接共用一把 `sync.RWMutex`。1000 人在线时这个 map 是**一个热点**——读锁虽然能并发，但写锁（有人上线/下线）会卡住所有人。

做法：拆成 16 个 map，按 uid 哈希分桶，每桶一把锁。

```go
const shards = 16

type Hub struct {
    buckets [shards]struct {
        sync.RWMutex
        conns map[string]*client
    }
}
```

改完压测，看高并发下 P99 有没有降。

### 改造三：找到这台机器的连接上限（不用改代码，10 分钟）

一直加 `-conns`，直到出现失败。记下那个数字和失败原因。

```powershell
.\bench\loadtest.exe -conns 5000 -msgs 1000
.\bench\loadtest.exe -conns 10000 -msgs 1000
```

**这个数字本身就是简历上的东西**："单机实测支撑 X 条并发长连接"。

## 八、跑完怎么记到简历里

不要写"支持 1 万并发"这种没跑的。写真实测到的：

> 独立实现秒杀结果推送服务（Go + WebSocket + Redis）：替代前端轮询，单机实测 2000 条并发长连接、消息零丢失，单连接内存占用 33 KB，端到端推送延迟 P50 16 ms / P99 32 ms。

面试官追问时你要能答的：

- **为什么用 WebSocket 不用轮询**：轮询每次都要建连接、带一堆 header，几万人在线时接口被自己打爆；WebSocket 建一次一直用。
- **2000 条连接占多少内存**：79.7 MB，平均 33 KB 一条。
- **消息会不会丢**：现在用的是 Redis 发布订阅（`Pub/Sub`），**会丢**——Go 服务重启那一下的消息收不到。生产环境应该换 `Stream` + 消费组，重启后能续上。
- **一台机器不够怎么办**：每台只持有本机在线用户的连接，Redis 广播到所有实例，谁有谁推；都没在线就落离线消息。

最后那条"我知道现在会丢"特别重要——**主动说出自己方案的缺陷，是可信度最高的表现。**
